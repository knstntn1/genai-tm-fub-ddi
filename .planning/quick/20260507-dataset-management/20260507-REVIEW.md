## Critical Issues

### CR-01: BLOCKER - DataExplorer dataset edits are not marked dirty

**File:** `src/components/DataExplorer/DataExplorerDialog.tsx:66`

**Issue:** DataExplorer mutates `datasetState` directly for create, delete, import, split changes, and image removal, but none of those mutations call the workspace dirty handling (`addCloseAlert` / save reminder) that class samples and behaviours use in `src/workflow/ImageWorkspace/Workspace.tsx:125`. A student can add or modify managed datasets, close or navigate away, and receive no unsaved-work warning or save reminder. This is a data loss risk for the new dataset management surface.

**Fix:**

```tsx
// Workspace.tsx
const markDirty = useCallback(() => {
    addCloseAlert();
    if (saveTimer.current === -1) {
        saveTimer.current = window.setTimeout(onSaveRemind, SAVE_PERIOD);
    }
}, [onSaveRemind]);

<DataExplorerDialog
    open={dataExplorerOpen}
    onClose={doDataExplorerClose}
    onChanged={markDirty}
/>
```

Then call `onChanged()` only after each successful `setDatasets` mutation in `DataExplorerDialog`, or wrap `datasetState` in a write atom that centralizes dirty marking.

### CR-02: BLOCKER - Datasets are saved even when sample saving is disabled

**File:** `src/workflow/ImageWorkspace/saver.ts:63`

**Issue:** `ModelSaver` passes `datasets` into `saveProject` regardless of `saving.samples`. The save dialog's sample checkbox explicitly controls whether training examples are included (`SaveDialog.tsx:15` and `SaveDialog.tsx:83`), but managed dataset images are still embedded in the ZIP when that checkbox is unchecked or when a variant disables sample saving. That is an incorrect save contract and can leak image data the user chose not to include.

**Fix:**

```ts
await saveProject(
    `${saving.name}.zip`,
    code,
    model,
    saving.behaviours ? behaviours : undefined,
    saving.samples ? data : undefined,
    saving.samples ? datasets : []
);
```

Add a saver test that unchecks `saveSamples` and asserts `project-datasets/manifest.json` is absent or empty, matching the intended project contract.

### CR-03: BLOCKER - Optional dataset ZIP failures make the whole project unloadable

**File:** `src/workflow/ImageWorkspace/loader.ts:20`

**Issue:** `loadProject` now loads the classifier project and optional managed datasets through one `Promise.all`. Any error in the optional dataset path rejects the whole load. `loadProjectDatasetsFromZip` can throw on malformed `project-datasets/manifest.json` JSON (`src/util/projectDatasets.ts:188`) or on a corrupt/unreadable dataset image (`src/util/projectDatasets.ts:201`). In those cases the model, labels, behaviours, and class samples could still be valid, but the loader reports "Could not load model" and leaves the project inaccessible. Optional dataset persistence should not break ZIP compatibility for the core project.

**Fix:**

```ts
export async function loadProject(file: File | Blob): Promise<Project> {
    const app = await ClassifierApp.load(file);
    const datasets = await loadProjectDatasetsFromZip(file).catch(() => []);

    return {
        id: app.projectId,
        model: app.model,
        behaviours: app.behaviours,
        samples: app.samples,
        labels: app.getLabels(),
        datasets,
    };
}
```

Also make `loadProjectDatasetsFromZip` defensive: catch manifest parse errors and skip individual images that fail to decode so one bad dataset image does not discard the entire project.

## Warnings

### WR-01: WARNING - Locale check script mutates files before failing

**File:** `scripts/addDataExplorerLocaleKeys.cjs:63`

**Issue:** The script merges missing locale keys and writes files at lines 63-65 before it checks `--check` at lines 69-72. A CI or preflight command using `--check` is expected to be read-only, but this implementation dirties the working tree before exiting non-zero.

**Fix:** In `--check` mode, compute drift without `fs.writeFileSync`, or build the merged JSON in memory and only write when `--check` is absent.
